# Отчет по лабораторной работе 2

## Цель работы

Сравнить подходы `threading`, `multiprocessing` и `asyncio` на двух задачах:

1. вычисление суммы чисел от `1` до `10000000000000`;
2. параллельный парсинг веб-страниц с сохранением заголовков в базу данных из `lr_1`.

## Задача 1. Вычисление суммы

### Реализация

- `threading_sum.py` создает несколько потоков и распределяет между ними диапазоны чисел;
- `multiprocessing_sum.py` использует пул процессов и вычисляет частичные суммы в отдельных процессах;
- `async_sum.py` создает набор корутин через `asyncio.gather`.

Во всех трех вариантах присутствует функция `calculate_sum()`. Диапазон от `1` до `10000000000000` делится на равные части. Каждая часть суммируется отдельно, после чего частичные результаты складываются.

Для выполнимости задания использована формула суммы арифметической прогрессии на каждом поддиапазоне:

```text
S = n * (a1 + an) / 2
```

Причина такого решения проста: полный последовательный перебор до `10^13` занял бы слишком много времени и не подошел бы для нормального учебного эксперимента.

### Особенности подходов

- `threading` удобен по синтаксису, но для CPU-bound задач в CPython ограничен GIL;
- `multiprocessing` обходит GIL и подходит для настоящего параллелизма на нескольких ядрах;
- `asyncio` хорош для кооперативного выполнения I/O-bound задач, но для CPU-bound вычислений ускорения обычно не дает.


### Комментарий

Для этой задачи `multiprocessing` остается самым корректным подходом по смыслу, потому что задача вычислительная. Но в конкретной реализации каждая подзадача считает сумму по формуле за `O(1)`, поэтому в измерении доминируют накладные расходы на создание потоков, процессов и корутин. Именно поэтому `asyncio` и `threading` здесь оказались быстрее `multiprocessing`.

## Задача 2. Параллельный парсинг веб-страниц

### Реализация

- `threading_parse.py` использует несколько потоков, каждый поток обрабатывает часть URL;
- `multiprocessing_parse.py` выполняет парсинг через пул процессов;
- `async_parse.py` использует `aiohttp` и `asyncio.gather` для конкурентных HTTP-запросов.

Каждая программа содержит функцию `parse_and_save(url)` и выполняет три действия:

1. загружает HTML-страницу;
2. извлекает содержимое тега `<title>`;
3. сохраняет заголовок в таблицу `tag` базы данных из первой лабораторной работы.

### Почему выбрана таблица `tag`

Из схемы `lr_1` именно таблица `tag` лучше всего подходит для хранения заголовков страниц:

- поле `name` естественно хранит текст заголовка;
- не требуется придумывать фиктивные денежные значения, как в `transaction`, `budget` или `goal`;
- в таблице есть уникальность `(user_id, name)`, поэтому повторный запуск не создает дубликаты.

### Таблица времени выполнения

| Подход | Команда | Время |
|---|---|---:|
| threading | `python -m lab2.threading_parse` | `1.412929 s` |
| multiprocessing | `python -m lab2.multiprocessing_parse` | `0.966960 s` |
| async | `python -m lab2.async_parse` | `0.686318 s` |

### Комментарий

Для сетевого I/O лучший результат в этом запуске показал `asyncio`, что соответствует ожиданиям: запросы выполняются конкурентно без лишней стоимости отдельных процессов. `threading` тоже работает корректно, но проигрывает по накладным расходам и планированию. `multiprocessing` оказался быстрее потоков, но все равно медленнее `asyncio`, потому что сетевой задаче не нужен полноценный процесс на каждую единицу работы.

## Вывод

- Для CPU-bound вычислений предпочтителен `multiprocessing`.
- Для сетевого I/O наиболее естественным решением является `asyncio`.
- `threading` остается простым компромиссным вариантом для задач, где важна простота и нужно ускорить ожидание ввода-вывода.
