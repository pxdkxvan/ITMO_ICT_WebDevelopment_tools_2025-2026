# Замеры и анализ

Замеры выполнены локально `12 мая 2026` командой:

```bash
python -m lab2.benchmark --workers 4
```

## Результаты задачи 1

| Подход | Время |
| --- | ---: |
| `threading` | `0.000822 s` |
| `multiprocessing` | `0.061046 s` |
| `asyncio` | `0.000067 s` |

### Комментарий

- задача вычислительная, поэтому с точки зрения модели параллелизма наиболее корректен `multiprocessing`
- в данной лабораторной сами подзадачи считаются по формуле за `O(1)`, поэтому доминируют накладные расходы на создание потоков, процессов и корутин
- именно поэтому в этом конкретном запуске `asyncio` и `threading` оказываются быстрее `multiprocessing`

## Результаты задачи 2

| Подход | Время |
| --- | ---: |
| `threading` | `1.412929 s` |
| `multiprocessing` | `0.966960 s` |
| `asyncio` | `0.686318 s` |

### Комментарий

- задача сетевого ввода-вывода естественно подходит под `asyncio`
- `threading` тоже хорошо работает на I/O-bound нагрузке, но здесь уступил из-за дополнительных накладных расходов
- `multiprocessing` показал средний результат: процессы дают избыточную стоимость для сетевого парсинга, но в конкретном запуске оказались быстрее потоков

## Итоговое сравнение

| Сценарий | Лучший результат | Причина |
| --- | --- | --- |
| Сумма чисел | `asyncio` в текущем замере | измеряется в основном overhead, а не вычисления |
| Парсинг страниц | `asyncio` | конкурентные HTTP-запросы без лишних процессов |

## Вывод

- `threading` удобен и прост, особенно для умеренного I/O
- `multiprocessing` подходит для CPU-bound задач, когда нужен реальный параллелизм по ядрам
- `asyncio` лучше всего раскрывается на сетевых запросах и других I/O-bound сценариях

С практической точки зрения лабораторная показывает не только различия API, но и важный инженерный вывод: подход нужно выбирать под тип нагрузки, а не по общему принципу "что быстрее".
